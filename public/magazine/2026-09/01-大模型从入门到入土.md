## 什么是大模型？（上）

提到大模型，我们常常会想到日常使用的DeepSeek、豆包、千问等AI工具。这些工具能够帮助我们完成多种多样的任务，如写作、搜索、整理等。不过，这些软件并不是所谓的"大模型"，而只是一个调用模型的接口。真正帮你干活的大模型在云端的服务器里跑着，而你手机上的软件只是把你的消息传到云端，然后根据云端大模型传回的信息执行相应的操作。流程如下：

我们可以看到，在这个流程中实际上干活的是在云端的大模型，而不是手机上的APP。这就要引出我们这一篇文章的主题了，大模型究竟是什么？

简单来说，大模型是一类参数量巨大的人工智能模型，它的作用是根据用户的输入内容进行运算，得到输出结果。而我们一般语境下的大模型指大语言模型（Large Language Model，LLM），它只进行文本的输入和输出。随着技术的进步，也涌现了大量的多模态大模型，可以进行图片、文字、语音等的输入和输出。或者输入文字、输出图片的文生图大模型，输入文字、输出语音的语音模型等。由此我们可以看到，大模型做的事情非常简单。给它一句话，它根据这句话进行运算，输出它的回复。而其它的联网搜索、排版渲染等功能都是外置工具干的事情。

还有一个需要纠正的误区是大模型是没有记忆能力的，你和大模型看似连续的对话，实际上是你每次和大模型对话的时候，软件把你们聊天的上下文全部发送到大模型那里，然后它根据上下文进行输出，达到了看似有记忆能力的功能。现在，我们来捋一捋在你使用APP和模型对话时，发生了什么。

## 场景一：简单的问好

第一步：你向DeepSeek软件发送“你好”。

第二步：软件对你的输入进行处理，添加时间、IP等信息。最后它会给云端发送类似如下信息：

```
{
{time:2026.9.1 13:20:18}
{location:Hebei China}
{device:mobile}
{message:你好}
}
```

第三步：云端接收到信息后，拼接上系统提示词等信息，合成如下：

```
{
{system:你是由深度求索公司研制的名为DeepSeek的大语言模型，具有一百万的上下文空间，相当于一部《三体》三部曲，你需要基于如下准则回答用户问题......}
{time:2026.9.1 13:20:18}
{location:Hebei China}
{device:mobile}
{message:你好}
}
```

第四步：服务器将这一大堆东西扔给大模型，大模型开始输出。类似如下文本：

```
{
<think>
我们需要回答用户“你好”。需要判断用户语言中文，简单问候。应友好回应，并询问需要什么帮助。保持简洁。不需要深入。
</think>
你好！我是**DeepSeek**，很高兴见到你，有什么可以帮你的吗？
}
```

第五步：客户端接收到这些东西之后，根据文本样式进行渲染，把<think> </think>中间的内容放置到“思考”栏目中呈现，其余放置于正文中。将两个**之间的文字进行加粗展示，最终呈现给用户。

在本场景中，你会发现，大模型仅仅起到了一个处理数据的作用，而不参与其它工作。但是仅仅可以进行输入和输出太无聊了，我们需要让大模型帮助我们干活，这就需要让大模型有调用工具的能力。很简单的实现方法是告诉模型，如果需要调用工具，就输出一个标记符，服务器读取这个标记符，执行相应的程序，然后把结果返回给大模型。样例如下：

## 场景二：天气询问

第一步：你向软件输入“今天天气怎么样？”并打开了联网搜索功能。

第二步：服务器向模型传入

```
{
{system:你是由深度求索公司研制的名为DeepSeek的大语言模型，具有一百万的上下文空间，相当于一部《三体》三部曲，你需要基于如下准则回答用户问题……如果你需要调用工具，请按照如下内容进行使用：Action: search, Action Input: query。}
{time:2026.9.1 13:20:18}
{location:Hebei China}
{device:mobile}
{message:今天天气怎么样？}
}
```

第三步：模型会输出如下结果：

```
{
<think>
用户问了今天天气怎么样……所以，让我需要搜索河北的天气。
<tool call>Action: search, Action Input: 河北 天气 2026.9.1 </tool call>
</think>
}
```

第四步：服务器识别到标记符，根据要求搜索了字符串并返回结果。这个结果包含全部上下文。

```
{
{system:你是由深度求索公司研制的名为DeepSeek的大语言模型，具有一百万的上下文空间，相当于一部《三体》三部曲，你需要基于如下准则回答用户问题......如果你需要调用工具，请按照如下内容进行使用：Action: search, Action Input: query。}
{time:2026.9.1 13:20:18}
{location:Hebei China}
{device:mobile}
{context:
user：今天天气怎么样？
Assistant：<think>
用户问了今天天气怎么样……所以，让我需要搜索河北的天气。
<tool call>Action: search, Action Input: 河北 天气 2026.9.1 </tool call>
</think>
}
{tool call result：
{看天气，用xx天气……}
{河北天气是……}
{……}
}
}
```

第五步：模型接收到这些东西，然后接着输出，最后把消息传回客户端，客户端进行渲染。

从如上案例我们可以发现，大模型本身仅仅完成输入输出的功能，而所有外部接口和调用的实现都是基于文本的。本样例仅仅展示简易过程，实际上模型的工具调用比这个复杂一些，但是原理是一样的。

{
<think>
我们需要回答用户：你好：。需要判断用户语言中文，简单问候。应友好回应，并询问需要什么帮助。保持简洁。不需要深入。

第五步：客户端接收到这些东西之后，根据文本样式进行渲染，把<think> </think>中间的内容放置到“思考”栏目中呈现，其余放置于正文中。将两个**之间的文字进行加粗展示，最终呈现给用户。

第六步：你向软件输入：你个大肥鱼！

第七步：服务器对你的上下文进行拼合，最终给模型输入类似如下内容：

```
{
{system:你是由深度求索公司研制的名为DeepSeek的大语言模型，具有一百万的上下文空间，相当于一部《三体》三部曲，你需要基于如下准则回答用户问题……}

{Assistant:<think>
我们需要回答用户“你好”。需要判断用户语言中文，简单问候。应友好回应，并询问需要什么帮助。保持简洁。不需要深入。
</think>
你好！我是**DeepSeek**，很高兴见到你，有什么可以帮你的吗？}
}
{message:你个大肥鱼！}
}
```

第八步：模型输出：

```
{
<think>我们需要理解用户输入。用户说“你个大肥鱼！”这看起来像是调侃或玩笑，可能不是严肃问题。需要回应得体，保持友好。用户可能是想测试或开玩笑。作为助手，应该以轻松幽默方式回应，不冒犯。可以顺着玩笑说，或者问是否需要帮助。注意语气。</think>
哈哈，我可不是鱼，我是AI助手，不过“大肥鱼”这个称呼倒是挺有趣的～
需要我帮你“游”向什么答案吗？😄
}
```

第九步：服务器将结果传回客户端，完成交互。

从此样例可以看出，模型是如何进行连续对话，显得似乎有记忆一样。通过对上下文的操作，我们可以很简单地实现消息撤回、修改等操作。而我们上传文件时，也是软件把文件处理为纯文本添加于上下文之中，传入模型。

然而，模型可以使用的上下文空间是有限的，上下文过长会导致巨量的算力消耗，也和模型的参数量等有关系，这些我们以后再说。
